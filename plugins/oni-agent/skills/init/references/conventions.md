# Mining an existing repo

Used in Phase 2, and only when the repo already has code. A greenfield project has no
conventions to find — it has decisions to make, which is Phase 3.

The job here is to write down what is currently **only in the maintainer's head**. That is
exactly what a fresh session gets wrong, and it is the highest-value thing this skill produces
for an existing codebase.

## Read first, ask second

Extract these by reading. Asking about any of them wastes the user's turn and reads as careless:

- Directory layout, and what each top-level folder is *for*
- Naming actually in use — not what the linter would prefer
- How errors are handled: exceptions, result types, error middleware
- How state moves: the data flow the codebase actually commits to
- Test layout, naming, and what "run the tests" means
- The boundaries someone clearly intended: what never imports what

Then ask only about intent that is not readable from code: what they regret, what is
half-migrated, which directories are legacy and must not be extended, and — the highest-value
question in the whole interview — **what a new contributor always gets wrong.** Its answer
becomes rules.

## Repeated structure is the main signal

When several features share a shape, that shape is the most valuable thing in the repo to write
down. It is also the thing most likely to be misread.

**How to find it.** Pick three or four features of the same kind — three endpoints, three
screens, three jobs — chosen from *different* times in the history, not three neighbours. For
each, list the files it touches and the order it touches them. What repeats across all of them
is a candidate. What appears in only the oldest is drift; what appears in only the newest is a
migration in progress, and it matters which direction it is going.

**Then stop, because a repeated shape is ambiguous.** It is one of two things and they demand
opposite treatment:

| It is | Signal | What to do |
| --- | --- | --- |
| A convention | Present in the newest code too; deviations look like mistakes; the maintainer can state why | Write it as a rule |
| Duplicated debt | Everyone copies the last one; nobody can say why it is that way; it is what they would fix given a week | Record it as an observation, not a rule |

Writing debt down as a rule is worse than saying nothing: it takes something the team wants to
escape and makes the agent enforce it forever.

You cannot tell these apart by reading. **Ask, per shape, and ask concretely** — show the
three files, describe the shape in one sentence, and ask whether a new one should look like
this or whether this is what they are stuck with. Do this per shape, not as one batched
question about "conventions", because the answer genuinely differs between them.

## What the linter already enforces is not a rule

Read the lint, format and type configuration before writing any style rule. Anything already
enforced by tooling is enforced; restating it in `CLAUDE.md` costs context on every session and
changes nothing.

Rules earn their place where tooling cannot reach: layering and import boundaries, which
directory a new unit of work goes in, what must never be edited by hand, the invariant that has
no test.

The same test applies to anything that must hold *every* time: that is a hook, not a rule. This
is the repo-wide position and it does not bend — instructions are context, hooks are
enforcement.

## Commit convention, read from history

Do not ask what the commit format is. Read it:

```bash
git log --no-merges -80 --pretty=format:'%s'          # subject lines
git log --no-merges -40 --pretty=format:'%s%n%b%n---' # subjects with bodies
git log --no-merges -200 --pretty=format:'%an' | sort | uniq -c | sort -rn
```

Merge commits are generated by the host and say nothing about the convention — exclude them.
Check the author spread too: a convention followed by one person across 200 commits is that
person's habit, and worth confirming before writing it as the project's rule.

Derive, from the actual lines:

- **Subject shape** — imperative or past tense, capitalised or not, trailing period or not
- **Prefix vocabulary** — the real set in use (`feat:`/`fix:`, `[Type]:`, an area prefix, or
  none), with the actual counts, not the set the user thinks they use
- **Length** — where subjects actually land, not what a style guide says
- **Body** — present routinely, only for large changes, or never
- **Trailers** — what is actually there, and whether it is on every commit or a handful
- **Issue references** — the form and where they sit

Then show the user the derived rule **next to five real subject lines it was derived from**, and
ask them to confirm. A convention read from history is a hypothesis; the maintainer knows
whether the last eighty commits represent what they want or what they settled for.

If history is inconsistent — two prefix styles, or none at all — say that plainly and offer to
settle one rather than inventing one silently.

### Never generate a machine-attribution trailer

**Do not write a rule that adds `Co-Authored-By: Claude`, `Generated with …`, or any other
generated-attribution trailer**, and do not add one to a commit yourself. This holds even when
the history contains them — those lines got there from a tool's default, not from a decision
anyone made, and propagating them into a rule makes the default permanent.

A human co-author trailer is a different thing and legitimate. If the history shows real
pair-authorship, record it as an observation about how the team works. Do not turn it into a
rule the agent applies on its own, because the agent cannot know who actually paired on a
change.

## Output

Everything in this phase lands in one of three places, and choosing correctly is the point:

| Finding | Goes to |
| --- | --- |
| Stack, layout, commands, the one-paragraph description | `CLAUDE.md` |
| A convention that stops a recurring mistake | `.claude/rules/`, `paths:`-scoped where it applies to a subtree |
| Something that must hold every time | A hook |
| Why the architecture is the way it is | `.claude/decisions/` |
| Debt the team wants to escape | A decision record marked `Status: Proposed` — never a rule |
